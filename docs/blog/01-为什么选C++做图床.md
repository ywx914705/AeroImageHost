# 从零手搓一个图床系统？我为什么选C++ —— AeroImageHost系列（一）

大家好，我是一名大三的计科学生。今天开始，我想用一个系列博客，完整记录我学习和拆解一个开源图床项目的过程。这个项目叫 **AeroImageHost**，是我目前在GitHub上见过的，用C++写的最完整的图床系统之一。

先说为什么写这个系列吧。之前做课设的时候，图床这个话题老是出现——"图片存哪？""怎么返回链接？""怎么让上传变快？"每次都是糊一个Node.js小服务就交差了。但说实话，心里一直不太满意，总觉得自己写的那些东西，经不起推敲。后来在GitHub上翻到了这个项目，一看——C++17写的图床？还带MinIO、Redis、Docker部署？这不得好好学一下？

## 先搞清楚：图床到底是个啥

如果你还不太清楚图床的概念，我用最简单的话说一下。

假设你在写一篇Markdown文档，想插入一张图片。Markdown本身不能"存"图片，它只能引用一个URL。那这个URL指向的图片存放在哪呢？——图床就是干这个的。你把图片上传到图床，图床给你一个链接，你在文档里贴这个链接，图片就能显示了。

听起来是不是很简单？上传→存→返回链接，三步搞定。

但真要做"好"一个图床，问题就来了：

- **上传的图片存哪？** 本地磁盘？对象存储？数据库？
- **多用户怎么隔离？** A用户的图片B能不能看？
- **大文件怎么处理？** 100MB的视频能不能上传？上传中断了怎么办？
- **图片预览怎么搞？** 传了一张4K图，列表页总不能加载原图吧？
- **安全怎么保障？** 别人暴力破解密码怎么办？恶意上传怎么办？

这些问题加在一起，一个小小的"上传+返回链接"就变成了一个完整的系统。而AeroImageHost，就是把这些问题的答案，用C++实现了一遍。

## 为什么用C++？这不多此一举吗？

我知道很多人第一反应是：写个图床，用Go、用Java、用Node.js不香吗？为什么要用C++？这不是给自己找麻烦吗？

说实话，我一开始也这么想。但读完这个项目的代码之后，我改变了想法。原因有三个：

### 1. 性能真的很炸

项目README里写了，内存占用只有80~120MB。这是什么概念？一个Spring Boot的Hello World，启动完就200MB+了。而AeroImageHost在这个内存下，能跑完整的HTTP服务、MySQL连接池、Redis缓存、MinIO交互、图片处理。

C++没有GC停顿，没有虚拟机开销，连接池和缓存可以做到非常精细的控制。这种资源效率，在云服务器上是实打实省钱的——4核4GB的机器就能稳定运行。

### 2. 对底层机制的掌控感

用Java写连接池，你用的是HikariCP；用Go写，你用的是sqlx里的pool。但在这个C++项目里，连接池是从零写的——`ConnectionPool`类，手搓的条件变量等待、懒验证、自动重建。

读这种代码，你是真的能理解"连接池到底在干嘛"，而不是把它当黑盒。这对学习来说，价值太大了。

### 3. 值得学习的工程实践

这个项目用了很多C++17的特性：`std::optional`、`std::unique_ptr`、结构化绑定、`std::atomic`……而且代码风格很统一，Google C++ style，模块划分清晰。作为一个学生，读这种项目，比读课本上的"学生管理系统"有用一百倍。

## 这个项目长什么样

先上一张官方的效果图吧。没登录的时候，页面是这样的：

![未登录页面](https://imagehost.aeroserver.ccwu.cc/api/i/0aa68d1d-afd0-48aa-b35c-600f26092375)

![登录后页面](https://imagehost.aeroserver.ccwu.cc/api/i/84bce7bf-6b36-4e46-920a-e315cb6e4fce)

功能上，它支持：
- 拖拽上传、粘贴上传、大文件分片断点续传

- 在线预览（缩略图、视频播放、PDF全屏）
- 文件搜索、排序、批量操作
- 永久链接分享，公开/私有切换

说实话，这比很多商业图床的功能还全。

## 技术栈一览

| 组件 | 技术 | 干啥的 |
|------|------|--------|
| 后端 | C++17 + Drogon | HTTP框架，处理请求 |
| 数据库 | MySQL 8.0 | 存文件的元数据（谁传的、多大、什么类型） |
| 对象存储 | MinIO | 真正存文件的地方，S3兼容 |
| 缓存 | Redis | 会话、限流、各种缓存 |
| 图片处理 | libvips | 生成缩略图 |
| 前端 | Vue 3 + Element Plus | 用户界面 |
| 部署 | Docker Compose | 一键部署 |

第一次看到Drogon这个名字的时候我还愣了一下——这是什么？后来一查，是腾讯开源的C++ HTTP框架，在TechEmpower的Web框架性能测试里排名很靠前。看来腾讯内部不少服务也在用它。

## 项目的目录结构

```
AeroImageHost/
├── CMakeLists.txt           # 构建配置
├── main.cc                  # 程序入口，所有服务的初始化和启动
├── http/                    # HTTP控制器和业务逻辑
│   ├── Controllers/         # 控制器（路由层）
│   ├── Filters/             # 过滤器（鉴权等）
│   ├── Handlers.cc          # 核心业务逻辑
│   └── Auth.cc              # Token认证
├── storage/                 # 数据访问层
│   ├── FileMeta.cc          # 文件元数据DAO
│   ├── UsersDAO.cc          # 用户DAO
│   └── MinIOClient.cc       # MinIO客户端
├── src/                     # 基础设施
│   ├── ConnectionPool.cc    # MySQL连接池
│   ├── RedisClient.cc       # Redis连接池
│   └── AeroQueue.cc         # 异步任务队列
├── image/                   # 图片处理
│   └── ImageProcessor.cc    # libvips封装
├── utils/                   # 工具类
│   ├── PasswordHash.cc      # PBKDF2密码哈希
│   ├── RateLimiter.cc       # 限流器
│   └── EmailSender.cc       # 邮件发送
├── monitor/                 # 监控
│   └── MetricsCollector.cc  # 指标采集
├── config/                  # 配置模块
├── schema/                  # SQL初始化脚本
├── www/                     # 前端SPA
└── docs/                    # 文档
```

这个结构很清晰。`http/`管路由和业务，`storage/`管数据，`src/`管基础设施，`utils/`管工具。每个模块职责单一，互不干扰。

## 我的学习计划

接下来的9篇博客，我打算按这个顺序来拆解：

1. ✅ **项目初印象**（就是这篇）
